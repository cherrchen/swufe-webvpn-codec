# 后续阶段设计备忘：TUN / 透明网关

> Status: Candidate ｜ Owner: cherrchen ｜ Last Reviewed: 2026-09-23

## 用途与状态

本备忘录整理未来评估 TUN / 透明网关时必须回答的问题，不定义当前需求、实现方案或发行承诺。其背景是 [PR-005](../requirements/product-requirements.md) 与 [ADR-0001](../architecture/adr/ADR-0001-wrd-rewrite-in-mitm-layer.md)：第一期不实现 TUN；若未来采用，分流内核不得承担 WRD 或 HTTP 内容改写。

是否启动后续 Feature、选择何种内核、支持哪些平台，均为 `TBD`。任何实施前都需要新建 Feature Spec，并按实际决策评估 ADR、安全模型与验收范围。

## 当前已知边界

- 当前流量接管方式是系统 HTTP/HTTPS 代理与按进程捕获；没有 TUN 接管能力。
- WebVPN 是应用层反向代理。请求改写与响应反向改写需要 HTTP 语义，继续由本机桥的 mitm 层负责。
- [ADR-0001](../architecture/adr/ADR-0001-wrd-rewrite-in-mitm-layer.md) 提出的候选职责划分是：TUN / 分流内核捕获并选择流量，将需要 WebVPN 的连接交给本机桥；内核不处理 WebVPN、WRD、Cookie 或响应正文语义。这是既有决策约束，不是已验证的 TUN 设计。
- 当前产品目标为 macOS 与 Windows；TUN 的平台支持、系统扩展/驱动授权和分发方式尚未评估。

## 后续设计需回答

1. **范围与路由**：哪些域名/IP/协议进入本机桥，哪些直连或丢弃？校内域名解析失败时，如何避免要求应用先自行解析？是否覆盖 UDP、IPv6 与本机流量？
2. **TLS 与协议边界**：如何只把需要检查的 HTTP(S) 流量送入 mitm 层？证书钉扎、非 HTTP 流量、QUIC/HTTP3 如何处理？对用户如何说明无法处理的连接？
3. **回环与共存**：如何确保桥到 WebVPN 的上游连接不会重新进入 TUN 路由？如何与系统代理、Clash/mihomo/sing-box 的 TUN 或其他 VPN 共存，冲突时怎样检测并安全失败？
4. **平台生命周期**：macOS Network Extension / Windows 驱动或系统服务所需的权限、用户同意、安装/升级/卸载、崩溃恢复和退出清理分别是什么？支持的 OS 版本范围是什么？
5. **安全与隐私**：TUN 捕获范围如何展示和缩小？如何限制本机监听、保护会话与 CA 私钥，并避免流量、DNS、正文或 Cookie 被不必要地记录？
6. **依赖与分发**：候选内核的许可证、维护状态、供应链、跨平台产物、体积、签名/公证要求和更新渠道如何评估？
7. **验证**：需要哪些 macOS 与 Windows 真机、路由/DNS/IPv4/IPv6、休眠恢复、冲突、卸载和故障注入验收用例？

## 设计原则

- 保持 TUN / 分流与 WebVPN 语义解耦；不把 WRD 编解码、Cookie 注入或正文反向改写放进 TUN 内核。
- 默认最小接管范围、用户可见授权、可逆安装/卸载，以及失败时不留下代理或路由残留，具体要求由后续 Spec 确认。
- 不因采用 TUN 就承诺任意 TCP/UDP 都能经学校 WebVPN 工作；WebVPN 能力边界仍需按具体协议确认。

## 输出与退出条件

本备忘录不是 Feature Spec，也不能据此开始实现。后续如启动设计，至少要形成：目标用户与使用场景、平台和权限模型、流量决策表、与现有桥的接口边界、冲突/回滚方案、依赖许可证评估及可复核的真机验证计划；所有尚未验证的结论标记为 `TBD`。
