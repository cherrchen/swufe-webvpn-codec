# ADR-0004: 系统代理被占用时拒绝启动

## Status

`Accepted`

## Date

`2026-09-20`

## Decision Owners

`cherrchen`

## Context

本机桥的第一条流量接管路径是把系统 HTTP/HTTPS 代理指向本地桥端口（REQ-003）：开桥前读取 OS 代理设置，设置 `127.0.0.1:<bridge_port>` 并保存「由本 App 设置」标记，关闭 / 会话过期 / 退出时仅在标记存在时清除（NFR-004）。但目标用户很常同时运行 Clash / mihomo / sing-box 之类工具，它们也争抢同一份系统代理设置。

与其它代理叠加后，流量路径变成「浏览器 → 第三方代理 → 本桥 → WebVPN」或相反，行为难以复现、难以测试，出错时也无法判断是哪一层改写或丢弃了请求；而静默覆盖用户的代理设置会让用户既失去原有科学上网/分流能力，又违反 NFR-004 对「不留半开代理」的要求。第一期已明确不与这些工具链式共存（NG 列表），因此必须在开桥路径上把冲突处理固定下来。

## Decision

启动桥之前检测系统代理状态；**若系统代理已启用且不是本 App 设置（未指向本桥端口），则拒绝启动桥**，并提示用户先关闭 Clash / mihomo / sing-box 等代理工具。

- 检测时机：每次 `startBridge` 之前，不缓存上一次结果；
- 冲突时返回 `PROXY_CONFLICT` 错误码，UI 以模态提示阻止继续（见 [main-window.md](../../ui-ux/main-window.md)）；
- 仅清除由本 App 设置过的代理：只有「由本 App 设置」标记存在时才在停桥 / 过期 / 退出时还原系统代理（NFR-004）；
- 禁止静默覆盖用户的代理设置；
- 链式共存不属于第一期范围；如需支持，必须新建 ADR 取代本条目；
- 执行责任人：cherrchen。

## Alternatives

| 备选方案 | 优点 | 缺点 | 未采纳原因 |
| -------- | ---- | ---- | ---------- |
| 什么都不做（不检测冲突，直接设置系统代理） | 实现成本为零；单次操作即可开桥 | 与 Clash / mihomo / sing-box 叠加后流量路径不可控、难以复现；退出时可能残留半开代理 | 违反 NFR-004，且叠加问题无法测试 |
| 与其它代理链式共存（本桥与第三方代理串联） | 用户可保留原有分流 / 加速能力 | 需要定义层序、分流边界与各自的证书信任关系，组合爆炸且难以覆盖测试；第一期无验收判据 | 难测，第一期不做（NG 列表） |
| 静默覆盖用户的系统代理设置 | 用户无感知，一次点击即可开桥 | 破坏用户既有代理工具与分流规则，且退出后是否还原完全依赖 App 自身 | 危险，且违反 NFR-004「不得留下半开代理」 |

## Consequences

### Positive

- 实现简单、行为确定：检测 → 拒绝 → 提示，没有中间态；
- 流量路径唯一，改写问题可归因，L2/L3 测试的判据清晰（TC-C 组用例）；
- 与 NFR-004 一致：只管理本 App 设置过的代理，不破坏用户既有配置。

### Negative

- 用户需在开桥前手动关闭其它代理工具，切换成本落在用户侧；
- 第一期无法与「同时使用 Clash / mihomo / sing-box」的场景共存，需在文案中提前说明。

### Risks

| 风险 | 可能性 | 影响 | 缓解措施 |
| ---- | ------ | ---- | -------- |
| 用户不理解冲突提示，误以为 App 不可用 | 中 | 中 | 模态文案直接给出「关闭 Clash / mihomo / sing-box 后重试」的可执行动作，并在高级设置中展示当前系统代理状态 |
| 检测到冲突但第三方工具随后释放代理，用户仍需重启开桥 | 低 | 低 | 冲突提示支持重试；不在后台自动轮询抢占代理设置 |
